## A.1 — Engineering Review

### Concurrency

**`@MainActor` على `PermissionsManager` و `BlockingEngine`** — ✅ صحيح. الأسباب:
- يتعاملان مع UI state (`@Published`) → يجب على Main Thread
- `AuthorizationCenter.shared.requestAuthorization` async — يمكن استدعاؤها من any actor، النتيجة على MainActor
- `ManagedSettingsStore.shield = ...` — Apple توصي بـ MainActor لـ shield updates

**`StoreManager` كذلك `@MainActor`** — ✅ صحيح:
- `@Published` properties
- `Transaction.updates` AsyncSequence ينتج VerificationResult — معالجته على MainActor آمن لتحديث `purchasedProductIDs`

**ملاحظة 1 (متوسطة):** في `StoreManager.handle(transactionResult:)`:
```swift
private func handle(transactionResult result: VerificationResult<Transaction>) async {
    if case .verified(let tx) = result {
        await tx.finish()
        await refreshEntitlements()
    }
}
```
هذا يُستدعى من `Task.detached` (deinit listener). الـ `@MainActor` على الـ class يجعل الاستدعاء يقفز للـ main thread — جيد، لكن قد يحدث reentrancy إذا تتالت transactions بسرعة. **الإصلاح المقترح:** غير حرج، حالة نادرة، يمكن إضافة actor reentrancy guard لاحقاً.

### Memory

**`BlockingEngine.stores: [UUID: ManagedSettingsStore]`** — ✅ مقبول:
- النمط الحالي يحتفظ بـ store لكل قائمة في memory
- `purge(listId:)` يزيلها من القاموس + يمسح settings
- لو حُذفت ListEntity من Core Data بدون purge → orphan store، لكن `deactivate/purge` تُستدعى دائماً قبل الحذف في `HomeView.deleteList`

**ملاحظة 2 (منخفضة):** لا cleanup عند `app terminates`. مقبول لأن `ManagedSettingsStore` تستمر في iOS بين تشغيلات التطبيق (هذا الغرض من ManagedSettings).

### State Machine

ListEntity حالات: `{idle, manualActive, scheduledInWindow, hardLocked, expired}`.

**الانتقالات الصحيحة:**
| من | إلى | محفّز |
|----|-----|-------|
| idle | manualActive | toggleManual (non-hard) |
| idle | hardLocked | save (now + hard + startImmediately) |
| manualActive | idle | toggleManual |
| hardLocked | expired | end of duration |
| expired | idle | عند تحديث الـ UI |

**ملاحظة 3 (متوسطة):** لا يوجد cleanup تلقائي للقوائم المنتهية. الـ `isActiveNow` يرجع false عند `now > end`، لكن:
- لا يُستدعى `BlockingEngine.deactivate(list:)` تلقائياً عند انتهاء الـ duration
- النتيجة: shield يبقى مطبّقاً حتى يفتح المستخدم التطبيق ويبدأ تفاعل

**الإصلاح المقترح (للنسخة 1.1):** Background task أو timer يفحص القوائم المنتهية ويستدعي `deactivate`. لـ v1.0، النتيجة المرئية (المستخدم يفتح التطبيق ويجد shield مطبّق) مقبولة لأن `manual override` يحلّها.

### Failure Modes

**ماذا يحدث لو فشل `ManagedSettings.shield = ...`؟**
- النظام لا يرمي exception — العملية تُعتبر idempotent
- لو الإذن مسحوب: shield لن يطبَّق لكن لا crash
- ✅ مقبول

**ماذا لو حُذفت ListEntity أثناء `activate()`؟**
- `activate(list:)` تستخدم `list.id` و `list.items` و `list.scheduleSlots`
- لو حُذفت من thread آخر بين الأسطر → crash محتمل
- ⚠️ نادر لكن ممكن

**الإصلاح المقترح:** التحقق من `list.isDeleted` في بداية `activate`. تُضاف في الفحص لكن **مقبول لـ v1.0** لأن:
- العملية على MainActor
- مسار الحذف يستدعي `purge` قبل `context.delete`

### Hard Mode Integrity

`BlockingEngine.deactivate(list:, force: false)` يرفض إيقاف Hard Mode إذا لم تنتهِ المدة — ✅ ممتاز.

`HomeView.deleteList` يفحص `isHardLocked` ويعرض رسالة منع — ✅.

`CreateListSheet` لا يتيح تعديل List موجودة (يُنشأ فقط) — ✅.

**ملاحظة 4 (منخفضة):** لا يوجد UI لـ "force deactivate Hard Mode" — هذا تصميم مقصود (الـ Hard Mode الفعلي).

## A.2 — Code Review (آخر diff)

### SQL/Data Safety
- Core Data merge policy: `NSMergeByPropertyObjectTrumpMergePolicy` ✅
- لا SQL خام ✅

### Conditional Side Effects
- `BlockingEngine.activate` — يطبّق shield ثم يجدول monitoring. لو الـ shield نجح والـ schedule فشل → القائمة مفعّلة جزئياً.
- ⚠️ **منخفضة الخطورة**: في حالة فشل startMonitoring (نادر)، الـ shield يبقى مطبّق ولن يُفك تلقائياً.

**الإصلاح للـ v1.1:** rollback shield عند فشل scheduling.

### Race Conditions
- `StoreManager.Transaction.updates` listener في `Task.detached` ينشَأ من `init` ويُلغى في `deinit` ✅
- `PermissionsManager` يستمع لـ `didBecomeActiveNotification` — لا تنازع: المعالج `Task { await refresh() }` MainActor ✅

### Force Unwraps
✅ تم إزالتها (HomeView, CreateListSheet)

### Error Handling
- `saveIfNeeded` مركزي مع `os.Logger` ✅
- `FamilySelectionStore.save` يلتقط encoding errors ويسجلها ✅
- `SchedulePersistence.decode` يرجع `[]` عند فشل decode مع log ✅

### Missing Tests
❌ سيُعالج في المرحلة C.

### Dead Code
- لا توجد دوال غير مستعملة بعد التنظيف ✅
- `subtitleText` في HomeView مع تعليق `/* kept for potential future use */` — مرشّح للحذف لكن مقبول

### Logging
- استخدام `os.Logger` بـ subsystem `app.nonet.blocking` ✅
- Categories: CoreData, BlockingEngine, Permissions, Store, AppleSignIn, SchedulePersistence, FamilySelection, ChatBot ✅
- لا `print()` متبقي في كود الإنتاج ✅
